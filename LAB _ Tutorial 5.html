Exercise

Tutorial 5

Below you can find the full exercise content together with downloadable attachments.

In this task, you build an ASP.NET Core Web API based on controllers. The goal is to practice routing, HTTP methods, model binding from route, query string, and body, as well as returning proper HTTP status codes. Data is stored only in memory, and the endpoints should later be tested in Postman.

Business Context

A training center organizes workshops and consultations in several classrooms. The coordinator needs a simple backend that allows them to manage the list of rooms and their reservations. At this stage, the system does not use a real database yet. The main goal is to design the API correctly and practice working with HTTP requests.

The application should allow users to browse rooms, filter them by selected parameters, add new entries, update data, delete rooms, and manage reservations. Initial data should be created when the application starts and stored in static lists.

Important. We do not use Entity Framework Core or an SQL database yet. The data source is a set of static in-memory lists prepared when the application starts.

What You Need to Build

Create an ASP.NET Core Web API application in C# that contains two controllers:

  • RoomsController for managing rooms,
  • ReservationsController for managing reservations.

Both controllers should work on data stored in memory. The data should be available right after application startup without manually adding records.

Suggested Data Models

Room

  • Id
  • Name
  • BuildingCode
  • Floor
  • Capacity
  • HasProjector
  • IsActive

Reservation

  • Id
  • RoomId
  • OrganizerName
  • Topic
  • Date
  • StartTime
  • EndTime
  • Status, for example planned, confirmed, cancelled

Required Endpoints

Rooms Controller

Method Endpoint Description GET /api/rooms Returns all rooms. GET /api/rooms/{id} Returns a single room by its identifier. GET /api/rooms/building/{buildingCode} Returns rooms from the selected building. The buildingCode parameter must be passed through the route. GET /api/rooms?minCapacity=20&hasProjector=true&activeOnly=true Returns rooms filtered by query string parameters. POST /api/rooms Adds a new room. PUT /api/rooms/{id} Updates the full room data. DELETE /api/rooms/{id} Deletes a room.

Reservations Controller

Method Endpoint Description GET /api/reservations Returns all reservations. GET /api/reservations/{id} Returns a single reservation. GET /api/reservations?date=2026-05-10&status=confirmed&roomId=2 Returns reservations filtered by query string parameters. POST /api/reservations Creates a new reservation. PUT /api/reservations/{id} Updates an existing reservation. DELETE /api/reservations/{id} Deletes a reservation.

Most important. The task must include different ways of passing data: id and buildingCode from the route, filters from the query string, and object data from the request body in JSON format.

Technical Requirements

1. Controllers and Routing

  • Use controllers with the [ApiController] and [Route("api/[controller]")] attributes.
  • Each operation should use the proper attribute, for example [HttpGet], [HttpPost], [HttpPut], and [HttpDelete].
  • In Program.cs, configure controllers with AddControllers() and map them with app.MapControllers().

2. Data Storage

  • Data should be initialized when the application starts.
  • The application should contain at least 4-5 sample rooms and 4-6 sample reservations in memory.
  • You may keep these lists directly inside the controllers or in one simple helper class.

3. Data Models

  • In this task, you may accept and return business models directly.
  • You do not need separate input and output classes.

4. Validation

  • Add Data Annotations to the classes used as input data.
  • Name, BuildingCode, OrganizerName, and Topic must not be empty.
  • Capacity must be greater than zero.
  • EndTime must be later than StartTime.
  • If input data is invalid, the application should return 400 Bad Request.

5. HTTP Status Codes

  • 200 OK for successful reads and updates,
  • 201 Created for successful creation of a resource,
  • 204 No Content for successful deletion,
  • 404 Not Found when a resource does not exist,
  • 409 Conflict when a reservation overlaps in time with an existing reservation for the same room.

6. Simple Business Rules

  • A reservation cannot be added for a room that does not exist.
  • A reservation cannot be added for a room marked as inactive.
  • Two reservations for the same room cannot overlap on the same day.
  • Deleting a room may return 409 Conflict if that room has future reservations, or you may use a simpler version and block deletion when any related reservation exists.

Suggested Project Structure

  • a Controllers folder with RoomsController and ReservationsController,
  • a Models folder for domain classes,
  • optionally one simple helper class for static lists if you want to keep data outside the controllers.

You do not need a complex architecture. The code should stay clear and simple. At this stage, most of the logic may remain directly inside the controllers.

Postman Test Scope

After implementing the application, test it in Postman. The goal is not just to call each endpoint once, but to verify the full workflow and the API response in different scenarios.

Minimum Set of Test Scenarios

  1. Get all rooms with GET /api/rooms.
  2. Get a single room by identifier.
  3. Get rooms by building code passed in the route.
  4. Filter rooms using query string parameters.
  5. Add a new room with POST.
  6. Update an existing room with PUT.
  7. Add a business-valid reservation.
  8. Try to add an overlapping reservation and verify 409 Conflict.
  9. Delete a reservation with DELETE.
  10. Verify the 404 Not Found response for a non-existing resource.

Important. In Postman, check not only the valid cases, but also invalid input data. This helps verify whether model binding, validation, and HTTP status codes work as expected.

What to Pay Attention To

  • Keep endpoint names and class names consistent and readable.
  • For POST, return 201 Created, preferably using CreatedAtAction.
  • For PUT, assume a full update of the object, not a partial update of one field.
  • If a resource does not exist, do not return 200 OK with an empty value. Return a proper error status instead.

What This Task Should Practice

  • designing a REST API in ASP.NET Core using controllers,
  • using the HTTP methods GET, POST, PUT, and DELETE,
  • model binding from route, query string, and body,
  • validating input data,
  • returning proper HTTP status codes,
  • testing API behavior in Postman.
